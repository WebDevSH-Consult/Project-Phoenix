# 0019 — Stream Deck Remote Control for a Two-PC Streaming Setup

## Status
Accepted

## Context
The streaming rig is split across two machines: the **gaming PC** (192.168.1.126) runs the game and has the Stream Deck plugged in by USB; the **streaming PC** (192.168.1.119) receives gameplay through an Elgato capture card and runs Streamlabs Desktop, which does the encoding and goes live. The capture card carries video only — nothing the Stream Deck does can travel over it.

The Stream Deck therefore has to control Streamlabs on *another* machine. The options checked:
- **Stream Deck hotkey actions** fire keystrokes on the PC the Deck is plugged into, so Streamlabs on the streaming PC never sees them.
- **Elgato's `com.elgato.streamlabs` plugin** (already installed) only drives Streamlabs *cloud* features — alerts, media share, spin wheel. It cannot go live, switch scenes or mute sources.
- **Streamlabs Desktop Remote Control** (Settings → Remote Control) exposes a token-authenticated JSON-RPC 2.0 API over SockJS on TCP 59650, listening on all interfaces. Verified from the gaming PC: `/api/info` reports WebSocket support, and an unauthenticated call is refused with "Authorization required. Use TcpServerService.auth(token)".

## Decision
Build a small Stream Deck plugin, **Phoenix Remote** (`streamdeck/com.projectphoenix.remote.sdPlugin`), that connects to the Remote Control API's raw WebSocket endpoint (`ws://<host>:59650/api/websocket`), authenticates with the token, and offers keys for go live/end, record, replay buffer, save replay, scene switching, audio mute and connection status.

- **Live feedback is the point.** The plugin subscribes to Streamlabs status events and also polls a small snapshot every 3 s, so a key never shows stale state if an event is missed or a subscription name differs between Streamlabs versions. Keys redraw only when state actually changes.
- **Safety on the irreversible key.** Go Live / End Stream needs a press-and-hold (0.8 s) by default; a short tap only shows "Hold to…". It can be turned off per key.
- **Names, not ids.** Scene and audio keys store the Streamlabs *name*, so the profile can be generated from `profile.json` before the plugin has ever connected, and a renamed item shows `MISSING` instead of silently doing nothing.
- **One art source.** Key images are SVG generated by `plugin/icons.js` (YakOS Aurora base blended with the Phoenix cosmic look). The plugin draws them live; `tools/build-icons.mjs` rasterises the static PNGs from the same code with headless Edge, keeping the plugin dependency-free.
- **HTML plugin (SDK v2), no build step.** Matches the existing installed plugins and needs nothing beyond the Stream Deck app.
- **Secrets stay out of the repo.** The token is entered by the user in the property inspector and stored in Stream Deck's global settings on the gaming PC. It is never logged.

## Alternatives Considered
- **Plug the Stream Deck into the streaming PC** and use Streamlabs' own local integration. Simpler wiring, but the Deck would sit away from the gaming setup, and game-side keys (Discord, Voicemod, Sonar) would then need a network link instead.
- **A third-party marketplace plugin** that reaches Streamlabs by IP. Rejected in favour of owning a small, auditable plugin with live state feedback and the Phoenix look; no dependency on a plugin that might stop being maintained.
- **A relay service on the streaming PC** (HTTP endpoints hit by Stream Deck "Website" keys). More moving parts, no state feedback on the keys, and another listening port to secure.

## Consequences
- The streaming PC must keep Remote Control enabled and allow inbound TCP 59650 — restricted to the gaming PC's address on the Private profile. Windows' "allow this app" prompt can recreate a broader rule after a Streamlabs update; check with `Get-NetFirewallRule -DisplayName "Streamlabs*"`.
- If the gaming PC's IP changes, the firewall rule and the plugin's host setting both need updating (a DHCP reservation avoids this).
- The Remote Control API is not formally versioned. Method and event names used here (`toggleStreaming`, `makeSceneActive`, `AudioService.getSources`, `setMuted`, `*StatusChange`, `sceneSwitched`, `sourceUpdated`) should be re-checked after major Streamlabs Desktop updates; the polling fallback limits the damage if an event name changes.
- This is the first piece of Phoenix that is not PowerShell workstation provisioning. It lives under `streamdeck/` and is installed by its own script rather than through a manifest; folding it into the Installer as an application manifest is a possible later step.
